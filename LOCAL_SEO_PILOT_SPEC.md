# Local Visibility Pilot — Build Specification

> Operational spec for a local-visibility outreach + delivery pilot. This is a
> business-process playbook, not a website feature. It follows the same honesty
> rules as the rest of the site: **no invented ranking impact, factual baselines
> only, no private lead data.** It complements the existing **VisibilityOS**
> product (the site's AI website visibility & conversion audit) and the
> `/automation` enquiry-handling systems — local visibility is the top-of-funnel
> that those systems convert.

## 1. Target list — do NOT reuse the current global hospitality list

Build a **new 50-business list in a single geography** (one city/metro). Do not
carry over the global hospitality outreach list as-is.

Recommended first test niches (pick one to start):
- Independent / boutique hotels.
- Restaurants with reservations or events.
- Auto services — **only if the owner is directly reachable**.
- Another local niche with high customer value and weak Google Maps visibility.

## 2. Qualification criteria (all must hold)

- Real, local service area.
- Independent or small group — **not** a global chain.
- Owner / GM / marketing contact is reachable.
- A Google Business Profile (GBP) already exists.
- Website and public facts can be independently checked.
- No active engagement from an earlier campaign.

## 3. Front-end message / offer

- **Do not sell "SEO."** Sell a short, concrete **visibility snapshot**: a few
  observable opportunities around the Google Business Profile, local page
  signals, and information consistency.
- Frame it as an observation of *what is publicly visible today*, not a promise
  of rankings or traffic.
- Keep it to a couple of specific, checkable points per business — no generic
  "you need more content."

## 4. Pilot delivery steps

1. **Baseline** — capture baseline screenshots / a local rank grid **only where
   lawful and available**. This is the factual reference point.
2. **GBP audit** — categories, services, description, hours, photos, and the
   review-request process.
3. **Website local relevance** — local page signals and on-page relevance check.
4. **Citations / NAP** — name-address-phone consistency across public listings.
5. **Prioritized implementation list** — ranked by observable impact vs. effort.
6. **Implement only the agreed pilot scope** — nothing beyond what the owner
   approves.
7. **Measure from the factual baseline** — report only what changed against
   step 1; **never invent ranking impact** or attribute unverified results.
8. **After trust is established**, discuss enquiry handling / follow-up
   automation (this is the bridge to `/auto-dealers`-style qualification and the
   `/automation` systems).

## 5. Honesty & data-handling rules

- No invented metrics, rankings, or before/after numbers. If a metric is not
  measured against the baseline, it is not claimed.
- Distinguish clearly: *observed today* vs. *proposed change* vs. *measured
  result*.
- **No private data**: do not store or publish private lead lists, unredacted
  messages, phone numbers, emails, credentials, or table data. Any example used
  publicly must be sanitized.
- The 50-business working list is internal operational data — it is not a
  website artifact and is never committed to the repository.

## 6. Acceptance criteria (per pilot)

- One geography, one niche, ≤50 qualified businesses.
- A factual baseline exists before any change.
- Agreed scope implemented and nothing beyond it.
- A short, honest snapshot deliverable per business (observations + prioritized
  list), with results measured only against the baseline.
- A clear, single next step offered (enquiry handling / follow-up) only after
  the snapshot has built trust.

## 7. Relationship to the website (no new product claims)

- This pilot is an **outreach + delivery process**, not a new website page or a
  new product. It does not require website changes.
- If it later graduates into a public offering, it should be surfaced through
  the existing **VisibilityOS** product rather than a separate "SEO" page, and
  any case study must follow the case-study system's honest status labels
  (`prototype` / `internal_pilot` / `real_client`) with a factual result or the
  standard "results still being collected" fallback.
